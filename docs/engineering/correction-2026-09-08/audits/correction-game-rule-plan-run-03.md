# Run 03 最小修规设计：游戏设计评议

评委 correction_game_final，2026-09-08。审查对象是 root 提出的五项修规设计，依据本席 run02 最终冻结 HTML 独立实测的 I1–I3，以及已批准 skill 的作答完整度、独立证据字段、后续任务和自由阅读要求。本次不修改 skill、公共组件或失败课件，不把设计批准当修复完成。

**结论：可以开始修 skill。五项方向直接覆盖根因；将下面的语义限定写进实际规则即可，不需要再增加题量、强制通关或一套新游戏机制。设计层无阻断 C/I。**

## 1. ready 与 judge 分离：解决提前冻结的直接原因

采纳。run02 只有 judge，没有判断本人是否填完，导致仅选 DE 即冻结并给剩余答案。ready 应返回本人待填的字段/组，judge 才返回数学差异；两个阶段不能共用“与正确答案匹配”作为通过条件。

建议把提交顺序写成：采集当前可信参考接触→检查当前条件的本人输入是否完整且候选合法→未 ready 时保留草稿、提示待填输入；ready 后才冻结提交与 assistanceAtSubmit→统一数学核对。未 ready 的点击可以保存草稿和真实参考接触，但不生成作答成绩、锁定答卷、标记答案已揭示或推进掌握/复习记录。

空路径集作为独立、明确的选择足够，不再添加二次确认弹窗。选择空集后 mapping 无所选行，因而没有对应映射待填；权重与固定分布格仍需填写。选择任何实际路径时，应取消空集选择，或规定二者互斥。判断完成度只看本人选择的行：允许提交完整但错误的路径集，不能借“缺了正确路径”把 ready 判失败并在提交前泄露标准集合。

缺映射时可以说“你选的 DE 尚未选 mean”，因为 DE 来自本人输入；不能说“还少 ED”来暗示正确路径。固定输出格的完成提示可以点名那个已展示的格，不补出其正确概率。

## 2. 四字段分开：解决辅助覆盖错误，而非改一条 if 顺序

采纳。correctness、assistance、resultSeen、skipped 需要各自保留事实；生成文案和推荐任务时才组合，不再先返回一个 assisted 枚举而丢掉错误。

两项必要限定：

- assistanceAtSubmit 是该次冻结答卷的提交前参考快照。之后打开反馈/全解仍增加当前可信接触，以供下一次尝试使用，但不追溯改写原先的提交。当前条件、当前答卷和旧历史不能混用。
- 保存了 main 预测但结果尚未呈现时，仍是“待核对”。即使内部已能计算其对错，也不能通过提前显示 repair 按钮或不同下一任务泄露判定。等到允许显示核对结果的阶段，任何错误无论参考与否都明确说明差异，并推荐当前条件修复；辅助事实附记。

“错误优先 repair”指推荐/默认接续，不是学习者必须通关的门槛。自由全解、跳过、退出和继续其他内容仍开放。skipped 应关联其实际轮次/当前未完成工作；历史曾提交与后来跳过可以同时存在，文案说明各自时点，不把旧提交悄悄删除成“从未作答”。

## 3. repair 四项合同：足以补接续，无需给每错题另造小测

采纳。当前错误、必要完整小步或可用原行入口、针对性重查目标、返回当前草稿/再试入口，正对应 run02 的缺口。

“完整小步或实际原行入口”二选一可避免把长推导复制第三遍。主例 repair 至少能到当前机制的真实原像与求和/约分行；构造 repair 的 missing/extra、权重和映射都保持当前条件与真实身份。重查目标具体到一个数学判断，例如“保留 DE，但排除 DD”或“给定第一抽后重新选第二因子”，而非只说“再看看”。

返回已冻结答卷时先诚实标“回看”；需要再答则走已有显式重试入口，保留旧答卷和接触。可以在原题草稿上完成针对性重查，不要求新增题量。重试是同题复核，不称新独立挑战。测试从实际错答进入 repair，打开原行，再用页面提供的返回/再试控件完成接续；评审直接调用 navigate 不能代替缺失的学习者控件。

## 4. 最终 DOM 交叉覆盖：必要但不必机械重复所有长推导

采纳。两组件×两机制×参考有无×对错，能直接发现 run02 的互斥枚举问题。列出 16 个情境的实际输入、参考来源、原提交与当前条件、显示事实、推荐目标及真实点击后的目标；可在一个测试函数或会话中复用步骤，但不能把“共用函数”当未运行另一机制的证明。

ready 边界单独测：零输入、仅选路径、漏本人所选行的一个映射、权重空、缺一个分布格；显式空集分别测其余输入未完和已完。完整错误答卷仍能提交，双击不新增，未完成输入不生成冻结/正确答案。这组边界针对构造组件即可，不必强行套到不含四组输入的 main 预测。

矩阵不是对所有事实求全笛卡尔积。main 未呈现结果、跳过和只观察另用必要边界场景覆盖；三类 repair 也分别覆盖其不同数学要求。相同代码路径可以合并运行和报告，但保留每个实际条件与结果的证据。沿用最终 hash 才有效、作者测试不替代独立审查、矩形/媒体 fixture 不等于浏览器实测的边界。

## 5. 必要控件边界对比：合理的独立可用性补充

采纳 root 指定的必要边界对比不低于 3 的约束。它不是前三项学习逻辑失败的原因，应单列为新增控件的实际可辨认检查，不扩大成重新设计全部数学角色颜色、装饰分隔线和图像。

按实际生效的 CSS、控件内外相邻背景、祖先背景和透明度计算；正常、选中及焦点状态中承担识别/状态表达的必要边界分别检查。仅报告样式表里某个被覆盖的 border 色值不能算通过。边界并非辨认控件或状态所必需的装饰，不因此强制加粗；也不以边界达标代替原有文字可读性要求。若实际背景无法由现有证据确定，应明确这一限制，不把 jsdom 冒充浏览器截图测量。

## 修改范围建议

把 ready/judge 与提交时点放入 interactive-html 的完整构造合同；把独立字段及 repair 接续放入 engagement-and-narrative；generation-checks 列本轮真实边界与交叉矩阵；新增控件必要边界放在现有视觉/控件约束附近。避免在多份文件重复粘贴五段近义要求，保持一处详细规则、其他处准确引用。

完成实际改文后仍需定点复审受影响规则和公共组件，再由新独立作者从空白生成；run02 成品维持退回。无需暂停来征求额外用户许可，也不新增一次蓝图/skill 通过就替代成品检查的例外。
